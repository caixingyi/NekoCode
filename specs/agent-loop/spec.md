# Agent Loop（ReAct 循环）需求说明

状态：已完成

## 背景

NekoCode step 1 做了对话内核，step 2 给它装上了工具系统，但 step 2 明确把「自动连环调用」留给了本章：每条用户消息内模型**最多被调用 2 次**（首次回复可能含工具调用 → 执行 → 回灌 → 再调一次得最终文本 → 停），第 2 次回复里若再出现 tool_use 直接忽略。

这意味着 NekoCode 现在还只能完成「读一下 X 文件」「帮我改 Y」这类**一步到位**的任务。真实的 agent 任务（「找出所有用到 X 的地方并统一改掉」「先跑测试，挂了就修，改完再跑」）需要模型连续多轮地"看 → 想 → 做 → 再看"，直到任务完成。

本章把单轮往返升级为真正的 **ReAct 循环**，并把循环本体从 TUI 里抽出来放进独立的 `internal/agent` 包：它以事件流对外暴露全过程，TUI 退化为事件消费者。这一步是后续所有能力（headless 模式、子 agent、MCP）的地基。

目标用户：希望 AI 能自主完成多步骤任务的开发者。

## 用户故事

- 作为开发者，我希望给 AI 一个多步骤任务后它能自己连续调用工具直到完成，而不是每步都要我催一次。
- 作为开发者，我希望看到循环的每一步在做什么（第几轮、调了什么工具、结果如何、花了多久），以便判断它有没有跑偏。
- 作为开发者，我希望循环遇到写操作时仍然逐个问我，并且我能随时打断。
- 作为开发者，我希望在动手之前先让 AI 只读不写，给我一份计划，我再决定要不要执行。
- 作为开发者，我希望循环卡住（原地打转、输出被截断、轮数跑飞）时能停下来并告诉我原因，而不是默默烧 token。
- 作为开发者，我希望中途打断或退出后，会话历史仍然完整可用，`/resume` 能接着聊。

## 需求

### 循环本体与事件流

- R1：实现 ReAct 循环：一轮 = 调用 LLM → 收到响应 → 若有工具调用则执行并把结果回填 → 进入下一轮；若本轮无工具调用则结束。轮与轮之间模型能看到全部历史（含之前的工具往返）。
- R2：循环以**事件流**（channel）对外暴露过程，上层按需消费。事件类型至少覆盖：用户消息、模型 thinking 增量、模型文本增量、工具调用开始、工具结果、轮次结束、当前循环结束、错误。
- R3：事件携带元信息：轮次序号、工具耗时、token 用量（本轮与累计）、工具批次号、停止原因。
- R4：循环本体位于独立的 `internal/agent` 包，**不依赖 TUI**，可脱离界面用 fake provider + fake tool 做确定性测试。

### 终止与收场

- R5：以下情形视为**正常终止**：模型显式 end_turn、本轮无工具调用、模型返回空响应（既无文本也无工具调用，允许只有 thinking）。
- R6：达到**轮数上限**（默认 25 轮）时停止循环，向用户提示「已达本轮上限」，用户可直接再发一条消息继续（历史保持合法）。
- R7：模型输出因**长度截断**（stop_reason = max_tokens）时不算正常结束：停止循环并向用户显式提示「输出被截断」。
- R8：**重复调用检测**：同一循环内**连续 3 次**出现完全相同的工具调用（工具名相同 + 参数相同，参数比较忽略 key 顺序）时，中止循环并提示用户。
- R9：**用户取消**（Esc / Ctrl+C）时立即停止循环：正在执行的工具被 context 打断，本批次中尚未执行的 tool_use 一律补一条「用户取消」的结构化结果，保证会话历史始终合法。

### 工具分批执行

- R10：一轮响应里含多个工具调用时按类别分组：**读类**（read_file / find_files / search_code）并发执行（并发上限默认 8），**写类**（write_file / edit_file / run_command）互斥串行执行。
- R11：调度顺序为「先并发跑完本批**全部读类** → 屏障 → 按模型给出的相对顺序**串行跑写类**」；无论实际执行顺序如何，结果**一律按模型给出的原始顺序**回填 tool_result 的 id 配对。
- R12：单个工具执行中 panic 必须被 recover 成结构化错误结果，不能让循环或进程崩溃。
- R13：写类工具逐个确认（沿用 step 2 的 y=允许 / n=拒绝 / a=本会话全部允许）；用户拒绝某个写类工具后，**本批剩余的写类工具全部跳过**并各补一条「用户拒绝」结果，循环继续把结果回灌给模型。

### plan-only 模式

- R14：提供 `/plan` 命令切换计划模式。该开关是**会话级状态**，随会话持久化；`/resume` 恢复会话时一并恢复开关状态。
- R15：计划模式下**工具定义照常全部下发给模型**，但在**执行时拦截**写类工具：回灌一条结构化结果，说明「当前为计划模式，写操作已被阻止，请直接输出计划而不要重试」；同时在界面上提示用户如何退出计划模式。
- R16：计划模式**不提供临时放行**：用户要执行写操作必须先退出计划模式。`run_command` 属于写类，计划模式下同样拦截。
- R17：计划模式下循环正常终止后，计划以**助手文本**形式留在会话中（不落盘为文件、不做「审批后一键执行」），后续是否执行由用户决定。

### 取消与超时

- R18：循环响应外部 context 取消，取消可发生在任意阶段（流式中 / 工具执行中 / 等待确认中），打断后循环状态必须自洽（见 R9）。
- R19：确认等待态下 Esc 表示「拒绝当前工具」，**不**取消整个循环。
- R20：工具级超时沿用 step 2（如 run_command 30s）；本章不引入循环级总超时，也不引入确认超时（用户不按就一直等）。

### 上下文与持久化

- R21：循环**内部不做自动压缩**。循环中检测到上下文接近上限时，中止循环并提示用户先 `/compact` 再继续；用户提交新消息前的自动压缩沿用 step 1 行为。
- R22：每轮结束落盘一次，保证中途退出或进程被杀后 `/resume` 拿到的是**合法且完整**的历史（tool_use 与 tool_result 始终配对）。
- R23：中间轮次的助手文本与最终回复同等对待：都渲染成独立的 assistant 消息并落盘。

### Provider 与工具元信息

- R24：provider 流式事件暴露**停止原因**（Anthropic `stop_reason` / OpenAI `finish_reason`），供循环区分 end_turn 与 max_tokens。
- R25：provider 暴露 **token 用量**（Anthropic 从 `message_start` / `message_delta` 取值；OpenAI 需在请求中开启 usage 回传）。
- R26：工具接口新增「是否只读」的显式声明，供 agent 分组；`run_command` 声明为非只读。

### 权限拦截位

- R27：在工具执行前后预留统一拦截位（pre/post 检查点）。本章只在 pre 位实现 **plan-only** 这一个具体规则，不实现其它权限规则。

## 验收标准

- AC1：「找出所有用到 X 的地方并改成 Y」这类多步任务，循环能自动连续调用工具直到完成并给出答复；会话里能看到每一轮的文本与工具序列。
- AC2：一轮里模型同时请求多个读类工具时并发执行；请求读写混合时先并发读、后串行写；结果按模型给出的原始顺序回填。
- AC3：一批写类工具中拒绝其中一个后，本批剩余写类被自动跳过并各回一条「用户拒绝」结果，循环继续并给出后续答复。
- AC4：循环中按 Esc / Ctrl+C 立即取消；未执行工具被补上「用户取消」结果；取消后立即发新消息、或退出重启 `/resume`，均不报错且历史完整。
- AC5：`/plan` 打开后写类工具被拦截并回灌提示，模型最终输出计划文本；退出计划模式后写操作恢复正常；`/resume` 恢复会话时开关状态一并恢复。
- AC6：轮数上限、连续 3 次重复调用、max_tokens 截断、空响应四种情形分别有明确的收场行为与用户提示，程序不崩溃、会话可继续。
- AC7：事件流覆盖 R2 列出的全部事件类型，且每个事件带 R3 要求的元信息（轮次序号、耗时、token 用量、批次号、停止原因）。
- AC8：Anthropic 与 OpenAI 两个 profile 都能跑通完整多轮循环，且 token 用量被正确解析与展示。
- AC9：循环中上下文超限时中止并提示 `/compact`，中止后的历史合法。
- AC10：`internal/agent` 可在无 TUI、无真实网络的情况下用 fake provider + fake tool 跑出确定性的循环测试（含并发分批、取消、plan 拦截、各终止条件）。

## 不做范围

- 复杂的系统提示词组装：本章沿用最小可用 system prompt，plan 模式也不通过 system prompt 告知模型。
- 完整的权限策略：除 plan-only 外只在工具执行前后留拦截位，不实现按工具/按路径的 allowlist，不做危险命令黑名单。
- 把 Agent 当工具递归调用（子任务委派）、子 agent、MCP、外部工具协议。
- 无头/非交互入口（如 `nekocode -p "..."`）：循环本体已无 TUI 依赖，但本章不交付 CLI 入口。
- 计划的落盘与「审批后一键执行」：计划只作为对话文本存在。
- 断点续跑：进程被杀后从半截循环继续（历史完整可读，但不自动续跑）。
- 循环级总超时、确认超时。
- 并发读的进度展示、工具完整输出的展开/折叠查看（沿用 step 2 的一行摘要）。
- 中间轮次的差异化渲染样式（所有助手文本同一套渲染）。
- 循环中自动压缩上下文（R21 明确不做）。

## 约束和假设

- Go 实现，延续 step 1/2 的 provider 统一抽象、bubbletea TUI、会话持久化与自动摘要。
- 需要支持工具调用与 stop_reason 的模型。
- 需要 provider 能拿到 token 用量（OpenAI 需显式开启 usage 回传）。
- 沿用 step 2 的 cwd 限制、y/n/a 确认、六工具行为与一行摘要呈现。
- 循环默认上限：25 轮；并发读上限：8。
- 确认必须由消费方提供；非交互消费方（本章不交付）不在范围内。

## 开放问题（已确认）

- 轮数上限后不做 `/continue` 之类的「一键继续」命令：用户直接再发一条消息即可，语义更直白。
- 被 plan 模式拦截的写类调用**计入** R8 的重复调用检测：模型反复重试同一个被拦的写操作，本质就是卡住。
- 轮数上限 25 与并发上限 8 本章写成 agent 包内常量，不进配置文件。
- 计划模式下模型可能完全看不到「计划模式」的存在（因为不碰 system prompt），只有碰壁才知道。接受这个代价（R15 已在拦截文案里明确要求输出计划）。
- 循环中上下文超限即中止、由用户手动 `/compact`：接受中断风险，保留后续在轮边界自动压缩的空间。
