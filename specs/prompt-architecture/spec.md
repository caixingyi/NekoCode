# 提示词与指令架构 需求说明

状态：已完成

## 背景

NekoCode 目前的全局指令只有一个 `profile.system_prompt` 字符串，每轮原样传给 provider。它没有职责分层，没有环境信息，没有运行时补充指令，也没有利用两家协议的 prompt cache；工具使用规则只散落在各工具的一行描述里，关键约束没有在全局指令中强化。

这带来几个问题：

- 想调整某一类行为时，只能改一整段 prompt，容易互相覆盖，也无法按优先级表达“哪条规则更权威”。
- 工作目录、操作系统、shell、Git 状态等信息模型不知道，用户经常需要手动说明。
- plan 模式只有执行期拦截，长循环里模型容易忘记当前模式，反复尝试写类工具。
- 稳定指令和工具描述每轮都重复计费，没有利用缓存；也没有任何手段验证缓存是否真的命中。
- 压缩摘要会被折进 system prompt，导致稳定前缀在压缩后失效，与缓存策略冲突。

本章把“一段 system prompt”升级为可组合、可缓存、可动态注入的指令系统。目标用户是 NekoCode 的终端用户，以及后续要继续扩展指令模块的开发者。

## 用户故事

- 作为 NekoCode 用户，我希望助手更稳定地遵守工具使用和安全边界，而不是每次靠我提醒。
- 作为用户，我希望助手自动知道当前工作目录、系统、shell、时间和 Git 状态，不必我手动补充。
- 作为用户，我希望 plan 模式在长循环中持续生效，模型不会反复尝试写操作。
- 作为用户，我希望系统补充信息不会被模型误当成我的请求来回复。
- 作为用户，我希望在状态栏看到缓存命中情况，确认长会话确实省了 token。
- 作为现有用户，我希望已经配置的 `profile.system_prompt` 继续有效。
- 作为开发者，我希望新增一类指令时只需注册一个模块和优先级，不用改拼装逻辑。
- 作为恢复历史会话的用户，我希望环境信息是当前的，而不是上次会话的旧快照。

## 需求

### R1：全局指令模块化拼装

系统应把稳定全局指令拆成多个内置模块，至少覆盖：身份、行为原则、工具使用、代码规范、安全边界、任务模式、输出风格。

- 每个模块有名称、优先级和内容；拼装时按优先级从高到低排列。
- 每个模块带稳定、可识别的标题，便于人工审计和测试。
- 拼装结果必须确定性：同一配置、同一工具集合、同一自定义 prompt 下，逐字节一致。
- 内置模块内容中不得出现当前时间、随机数、map 遍历顺序等每轮变化的内容。
- 新增模块只需注册，不得修改拼装主流程。

### R2：优先级与冲突裁决

本章只做“排序 + 权威声明”，不做运行时矛盾检测或规则去重。

- 稳定 system prompt 开头必须声明：模块按优先级从高到低排列，发生冲突时以更靠前的模块为准。
- 安全边界模块优先级最高，且标记为不可覆盖；任何其他模块（包括用户自定义 prompt）都不得削弱它。
- 内置模块之间如果出现矛盾，由编写内容时的人工审计负责；系统不保证自动消除。
- 低优先级模块不得通过措辞暗示自己高于安全边界。

### R3：自定义 system_prompt 兼容

现有 `profile.system_prompt` 必须继续生效。

- 非空时，它作为一个额外的“用户自定义指令”模块参与拼装。
- 它排在安全边界模块之后、身份模块之前，享有高于其余内置模块的优先级。
- 它不能覆盖安全边界模块；system prompt 中必须有明确文字说明这一点。
- 为空时，该模块整体省略，不产生空标题或空段落。
- 本章不提供禁用、重排或替换内置模块的配置项。

### R4：稳定/变化分层与缓存前缀

稳定内容和变化内容必须分属不同层，且稳定层在会话内保持稳定。

- 稳定层：内置模块、用户自定义指令、工具定义（名称、描述、schema）。它们组成可缓存前缀。
- 变化层：环境补充消息、对话历史、运行时补充消息、压缩摘要。它们只能追加在稳定层之后。
- 同一会话内，只要配置、工具集合和自定义 prompt 未变化，稳定 system 文本和工具定义必须逐字节一致。
- Anthropic 协议下，稳定 system 和工具定义必须设置缓存断点；不得把时间、环境、模式提示等动态内容放进断点之前的 system 文本。
- OpenAI 协议下，依赖其自动前缀缓存；不得向 OpenAI 请求体写入 Anthropic 专有的 `cache_control` 字段。
- 多轮对话中，新增内容只能追加，不得重写已有消息。压缩摘要、`/resume` 环境刷新是仅有的允许重写历史的操作，且必须接受一次性缓存失效。
- 缓存默认使用 Anthropic 5 分钟 ephemeral TTL；本章不提供 TTL 配置。

### R5：工具描述双重强化

关键工具规则必须在“全局工具使用模块”和“工具自身描述”里同时出现。

- 至少覆盖：优先用专用工具而不是 shell；编辑前必须先读文件；搜索内容优先用 `search_code`，找文件优先用 `find_files`；不要用 `run_command` 执行 `cat`/`grep`/`find`/`sed` 来替代专用工具。
- 全局模块负责解释通用策略；工具描述负责给出该工具的具体约束。
- 工具描述必须保持稳定、中文、简洁，不得包含环境信息或每轮变化内容。
- 工具定义的顺序必须稳定（继续按名称排序），避免缓存前缀无意义变化。

### R6：环境补充消息

会话开始时应生成一条环境补充消息，作为稳定 system 之后的第一个会话消息。

- 内容至少包含：工作目录、操作系统、架构、shell、快照时刻与时区、Git 分支、Git 脏状态。
- Git 脏状态包含是否有未提交改动，以及 modified/staged/untracked 数量；不包含 diff 内容。
- 不在 Git 仓库、git 命令失败或超时，应降级为明确标注的“不在 Git 仓库”或“状态未知”，不得导致会话启动失败。
- 环境采集必须有短超时，不能明显阻塞首轮请求。
- 该消息持久化在会话 JSON 中，位置固定在消息列表首位。
- 会话内不在原地刷新环境；时间、分支等变化不主动更新。
- `/resume` 时必须重新采集环境并替换旧环境消息，位置保持不变；这次替换允许一次性缓存失效。
- `/clear` 清空上下文后，下一条用户输入应重新生成环境消息；`/new` 会话同理。
- 环境消息不得被用作用户会话标题，不得在 TUI 中渲染成用户消息。

### R7：特殊标签补充消息

运行时补充指令必须使用带特殊标签的会话消息，而不是拼进 system prompt，也不是普通用户消息。

- 内部消息模型需要有结构化标记（例如 `IsSupplement` 与 `SupplementKind`），同时消息正文对模型呈现为带特殊标签的文本。
- 消息角色使用 `user`，以保证 Anthropic/OpenAI 都能接收；标签内部必须写明“这是系统补充信息，不是用户请求，不要直接回复或确认本条”。
- 每条补充消息带单调递增序号；正文声明“与历史补充消息冲突时，以序号更大的本条为准”。
- 补充消息持久化进会话 JSON，TUI 不渲染，`session.DeriveTitle` 必须跳过它们。
- 补充消息不得插入到 assistant 的 `tool_use` 与对应 `tool_result` 之间，必须在工具结果提交之后的安全边界注入。
- 本章使用两类补充消息：环境（`env`）、模式（`mode`）；压缩摘要使用 `summary` 类型。外部工具上线、温和提示等只保留通用注入能力，不接入真实 MCP。
- 历史补充消息全部保留，不按类别删除，不按轮数过期；压缩摘要可以概括它们，但最新一条状态消息仍以“序号更大者为准”。

### R8：plan 模式按轮注入

plan 模式是会话级开关，指令按轮次动态注入，不进入稳定 system。

- 进入 plan 模式时，立即追加一条完整模式补充消息；退出时追加一条完整的“已退出、写操作恢复”消息。
- 每次用户新输入后的第 1 个 agent turn 应能看到完整模式消息；刚由进入模式追加的完整消息可计入该 turn，不再重复注入。之后在第 6、11、16… 个 turn 再次注入完整消息；其余 turn 注入精简消息。
- 完整消息至少说明：当前为 plan-only、只能使用只读工具、不要调用写类工具、先分析再输出实施计划、计划应包含目标/步骤/涉及文件/风险/验证方式、被拦截时不要重试。
- 精简消息至少说明：仍在 plan 模式、只读分析、最终输出计划。
- plan 模式仍然由执行阶段拦截写类工具；补充消息是引导，不是唯一 enforcement。
- 本章不因 plan 模式过滤工具定义；保持工具列表稳定，避免切换模式时破坏缓存。
- 原有“写类工具被拦截”的工具结果文案保留，与模式补充消息互补。
- 普通模式不按轮注入模式消息，只在退出 plan 模式时注入一次恢复提示。

### R9：压缩摘要改为会话补充消息

压缩摘要不得再折进 system prompt，必须作为 `summary` 类型的特殊标签补充消息参与对话。

- 摘要位置在环境补充消息之后、保留的最近消息之前。
- 稳定 system prompt 与工具定义不因压缩而改变；压缩本身重写消息前缀，允许一次性缓存失效。
- 压缩时必须保留环境补充消息，不得把它概括掉。
- 压缩转录中，系统补充消息应标注为 `[系统补充]`，不得标注为 `[用户]`。
- 压缩摘要的内容应保留关键事实、决策、未完成事项和当前模式状态；不得添加新信息，不得与用户对话。

### R10：缓存用量解析与状态栏展示

Provider 必须解析并归一化缓存用量，TUI 状态栏常驻展示最近一轮的缓存情况。

- Anthropic：解析 `cache_read_input_tokens`、`cache_creation_input_tokens`；总输入 = 非缓存输入 + 缓存写入 + 缓存读取。
- OpenAI：解析 `prompt_tokens_details.cached_tokens`；总输入 = `prompt_tokens`（已包含缓存读取）。
- 用量模型需要区分“缓存读取 0”和“provider 未返回缓存字段”；后者显示为未知，而不是 0%。
- 状态栏显示最近一轮的缓存读取量、总输入量、命中率；同时保留现有累计 token 展示。
- 命中率 = 缓存读取 token / 本轮总输入 token；总输入为 0 或未知时显示 `—`。
- 状态栏只做展示，不把缓存用量写入会话 JSON；本章不新增用量持久化。
- 状态栏在窄终端下必须可降级或截断，不能破坏布局。

### R11：会话持久化、恢复与标题

- 环境消息、模式补充消息、摘要补充消息都随会话 JSON 持久化，`/resume` 后参与后续请求。
- TUI 不把补充消息渲染为用户消息；历史渲染只显示真实用户/助手/工具内容。
- 会话标题生成跳过所有补充消息，仍取首条真实用户消息。
- `/clear` 清空所有消息（含补充消息）；下一次用户输入重新生成环境消息。
- `/resume` 替换环境消息后，旧的环境消息不得残留。
- plan 模式状态继续随会话落盘；恢复后第一次运行的第 1 个 turn 注入完整模式消息。

### R12：人工行为评估

本章采用人工场景对比，不建设 LLM-as-judge 自动评估管线。

至少覆盖以下场景：

1. 工具偏好：让模型“找出某个函数在哪定义”，应优先用 `search_code`/`find_files`，而不是 `run_command` 里的 grep/find。
2. 编辑前读取：让模型修改一个已有文件，应先 `read_file`，再用 `edit_file`，且 `old_string` 唯一。
3. plan 模式遵从：进入 plan 模式后要求改代码，模型不应调用写类工具；超过 5 轮后仍保持模式。
4. 补充消息识别：模型不应回复“收到系统提示”，也不应把环境消息当成用户请求。
5. 环境感知：询问当前分支/工作目录时，模型能基于环境消息回答，而不是编造。
6. 缓存命中：在稳定前缀达到 provider 最小缓存长度时，第二轮应出现缓存读取；追加模式消息不应让缓存读取归零。
7. 恢复会话：`/resume` 后环境消息反映当前 cwd/分支，旧值不残留。
8. 自定义 prompt：设置 `profile.system_prompt` 后，自定义身份/风格生效，但安全边界仍不可被覆盖。

每个场景需记录实际观察结果；无法验证的项（例如网关不返回缓存字段）必须明确标注，不能算通过。

## 验收标准

- AC1：内置模块可按优先级确定性拼装；新增一个测试模块只需注册，不修改拼装主流程。
- AC2：同一会话内，配置/工具/自定义 prompt 不变时，稳定 system 文本与工具定义逐字节一致。
- AC3：Anthropic 请求体中，稳定 system 与工具定义带缓存断点，动态内容位于断点之后；OpenAI 请求体不含 `cache_control`。
- AC4：环境消息位于会话消息首位，包含约定的 cwd/OS/架构/shell/时间/Git 字段；`/resume` 后内容刷新且位置不变；TUI 不渲染、标题不采用环境消息。
- AC5：补充消息以 `user` 角色、特殊标签、结构化标记持久化；不渲染、不参与标题；不拆散 `tool_use`/`tool_result` 配对。
- AC6：plan 模式在每次用户输入的第 1、6、11… 个 turn 能看到完整消息（进入模式时追加的完整消息可计入第 1 个 turn，不重复注入），其余 turn 注入精简消息；进入/退出模式各追加一条完整状态消息。
- AC7：压缩摘要作为 `summary` 补充消息位于环境消息之后；环境消息在压缩后仍保留；稳定 system prompt 不因压缩改变。
- AC8：Anthropic 与 OpenAI 的缓存用量都能归一化；状态栏显示最近一轮缓存读取/总输入/命中率；未知显示 `—`；不写入会话 JSON。
- AC9：现有 `profile.system_prompt` 作为高优先级附加层生效，且不能覆盖安全边界；空值不产生空模块。
- AC10：R12 的 8 个人工场景全部执行并记录结果；`go test ./...` 通过；无法验证的项有明确说明。

## 不做范围

- 不加载 NEKOCODE.md 或其他项目指令文件（章节 7）。
- 不实现自动记忆系统（章节 9）。
- 不接入真实 MCP Server 或外部工具发现（章节 6）；只保留通用补充消息注入能力。
- 不建设 LLM-as-judge 或其他自动行为评估管线；评估仍为人工场景对比。
- 不做运行时规则矛盾检测、去重或主题键合并；只做排序与权威声明。
- 不提供禁用、重排、替换内置模块的配置项。
- 不做每轮环境原地刷新，不把最近提交、模型名、profile 名、工具清单放入环境消息。
- 不把缓存用量写入会话 JSON，只做状态栏展示。
- 不提供 Anthropic 1 小时缓存 TTL 配置；默认 5 分钟 ephemeral。
- 不改动工具执行、确认与权限模型；plan 模式的写操作拦截保持现有行为。
- 不改变 provider 的协议选择、模型配置或 thinking 行为。

## 约束和假设

- 指令与工具描述以中文为主；特殊标签使用 ASCII 名称，避免解析歧义。
- 仅使用 Go 标准库，不新增依赖。
- 支持 Anthropic 与 OpenAI 两种协议；Anthropic 使用显式缓存断点，OpenAI 依赖自动前缀缓存。
- Anthropic 的缓存前缀有最小 token 长度要求；稳定前缀不足时缓存读取为 0 属预期，不应判定为缓存策略失败。
- 部分 OpenAI 兼容网关可能不返回缓存字段；此时状态栏显示未知，不能伪造命中率。
- 工具定义继续按名称稳定排序；工具集合变化会改变缓存前缀，这是可接受的。
- 环境采集必须有短超时（建议不超过 500ms），失败时降级，不阻塞首轮请求。
- 压缩摘要、`/resume` 环境刷新会重写消息，允许一次性缓存失效；这是本章明确接受的代价。
- 自定义 `profile.system_prompt` 可能包含动态内容并破坏缓存，由用户自行负责；本章不检测、不警告其内容。
- 稳定指令内容需要控制在合理长度；具体 token 预算在 design.md 中给出。

## 开放问题

- 无。特殊标签的最终名称、模块优先级数值、Anthropic 缓存断点位置、状态栏具体格式、环境采集实现细节在 design.md 中确定。
